The PHP patch is out. Update today.

PHP runs about 7 in 10 websites. Two bugs inside PHP itself let a stranger take over a web server without logging in. PHP shipped the fix at 14:00 UTC on 21 October; attacks were seen about six hours earlier.

Fixed releases: 8.5.12, 8.4.27, 8.3.36, 8.2.35 or later.

Meaning

A memory mix-up inside PHP hands a stranger the server

PHP reuses the same worker for request after request. Both bugs are about clean-up: when a request fails in an unusual way, PHP can leave behind scraps of memory it still trusts. A later request can pick them up. An attacker who arranges this can run their own commands on the server with the same rights as the website.

No password or account is needed, and the website's own code does not have to be faulty. A fully updated WordPress on an old PHP is still exposed.

CVE-2026-109618

Out-of-memory clean-up

9.2of 10, PHP's rating

PHP's title: RCE via OOM corruption. When a request runs out of memory, PHP can treat half-built data as valid while cleaning up.

CVE-2026-109619

Leftovers between requests

9.2of 10, PHP's rating

PHP's title: RCE via stale global state. Data from one request can outlive its memory and be used by the next request on the same worker.

RCE: remote code execution, running commands on someone else's computer. watchTowr rated the bugs 10.0. Sansec reports one path can also leak memory from other visitors' requests, such as passwords and session tokens.

Timeline

Fourteen years hidden, ten weeks to fix, six hours of attacks before the patch

The weakness was noticed more than once and left alone because nobody showed it could be used. In 2026 researchers working with AI models showed it could. Wiz credits frontier AI models with lowering the cost of turning the bug into an attack.

    Who

    Half of PHP websites got a ready-made fix. The other half need a hand patch or an upgrade

    PHP shipped new releases only for the branches it still supports, 8.2 to 8.5. For 7.4, 8.0 and 8.1 it published a bare source patch: useful to people who build PHP themselves or have a vendor who backports it, of little use to most site owners. Older branches get nothing.

    Fix

    Update PHP, restart every PHP process, then check

    A running PHP process keeps the old code in memory until it restarts. An update without a restart leaves the hole open.

      If you cannot patch within the hour

      These buy time. None makes a server safe.

      ☁️ Cloudflare in front

      Cloudflare added firewall rules for the known attacks on every plan, the free one included. Its CTO calls them a stopgap.
      Cost: covers only traffic that goes through Cloudflare.

      ⚙️ php.net's interim settings

      The advisory lists settings that close some paths, applied in php.ini or the FPM pool with every worker restarted. Read them on php.net.
      Cost: partial, and some trade memory safety for availability.

      🚫 Turn off uploads

      Sansec suggests refusing file-upload requests at the web server for a while.
      Cost: breaks the media library, product photos, and some forms and checkouts.

      🔌 Take it offline

      The UK NCSC advises taking offline any system that cannot be fixed now. Serve a static maintenance page with PHP stopped; WordPress and Magento maintenance modes still run PHP.
      Cost: the site is down until patched.

      After patching, look for a break-in

      Attacks began before the fix, so a patched server can already hold an intruder.
